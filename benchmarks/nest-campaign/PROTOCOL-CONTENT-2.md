# NEST campaign, content part: protocol 2

Status: fixed on 2 November 2026, before the recorded trials.
Its SHA-256 is in [`PROTOCOL-CONTENT-2.sha256`](PROTOCOL-CONTENT-2.sha256). The schedule records the same digest.
Do not edit this file. Record any deviation in the README.

## Question

Does NCP 2 deliver exactly the spikes that NEST simulated, the same neurons at the same times, with its Python host and with its Rust host?

## Why

The [content protocol](PROTOCOL-CONTENT.md) compared every spike only for NCP 1.0.1 and MUSIC. Its NEST owner selected the spikes of each interval by time from the recorder's events.
Protocols 2 to 5 use another readback, which reads the recorder's ASCII files, and they check only that the number of spikes at the host equals the recorder's total.
A count can be right while a time or a neuron is wrong.

## Method

For each configuration, [`harness/content2.py`](harness/content2.py) runs three processes with the same network and seed:

- **reference:** NEST alone runs 2 s in one call, and its spike recorder's complete events are kept;
- **ncp2-py:** the NCP 2 Python host [`harness/ncp2_host.py`](harness/ncp2_host.py) drives the NEST owner [`harness/ncp2_owner.py`](harness/ncp2_owner.py) with the payload `spikes`, and the host keeps every received (neuron, step) pair;
- **ncp2-rs:** the NCP 2 Rust host [`harness/ncp2-rust`](harness/ncp2-rust) does the same.

The owner and the hosts are those of protocols 3 to 5, with the NCP 2 SDKs of the commit that the schedule records. The owner reads the new spikes after each interval as in protocols 2 to 5. It checks the digest of each request, and the hosts check the digest of each response.
The comparison uses exact multisets of (neuron, time) pairs, with times rounded to 0.1 µs. A received step k is the time k × 0.1 ms. Neurons are numbered from the first neuron of the network.

## Configurations

- The 24 configurations of the content protocol: the networks `alpha`, `brunel`, and `aeif` with 1000 neurons, 1, 2, 4, or 8 NEST threads, and Δ = 1 or 5 ms.
- `brunel` with 10,000 neurons, 1, 2, 4, or 8 threads, and Δ = 1 or 5 ms: 8 configurations. With Δ = 5 ms, some of its steps exceed the 65,536-byte frame of NCP 1.0.x.

This gives 32 configurations. Three blocks run each configuration once; block b uses the network seed 20261025 + b, as in the content protocol. The order of each block is shuffled with the seed 20261102.
The runner is `content_run.py --protocol 2`, and the analysis is `analyze_content2.py`.

## Smoke trials that informed this protocol

On 2 November 2026, one trial each ran for `brunel` with 1000 and with 10,000 neurons, 4 threads, Δ = 5 ms, and the seed 20261025.
Both hosts received exactly the reference multiset: 116,641 and 715,849 spikes. The first reference total equals that of block 0 of the same configuration in the content protocol.
In the received pairs of the first trial, a change of one step by 0.1 ms, or of one neuron, made the comparison fail, while the number of spikes stayed equal to the recorder's total.
A test of the runner then ran four trials of block 0 (`brunel` with 10,000 neurons, 8 threads, Δ = 5 ms; `alpha`, 2 threads, Δ = 5 ms; `aeif`, 2 threads, Δ = 1 ms; `brunel`, 8 threads, Δ = 5 ms), and both hosts received exactly the reference multiset in each.
These trials are not results.

## Hypotheses

- **K1.** In every trial, the NCP 2 Python host receives exactly the reference multiset.
- **K2.** In every trial, the NCP 2 Rust host receives exactly the reference multiset.
- **K3.** For each of the 24 configurations of the content protocol and each block, the reference total equals that of the content protocol.

A hypothesis holds when its criterion holds. A trial that fails to run is reported, and then no hypothesis holds.

## Not claimed

The result covers these networks, sizes, thread counts, and intervals, with the payload `spikes` of the campaign harness, on the computer of the campaign. It times nothing.
