## Why a second protocol

Run 1 of [protocol 1](PROTOCOL.md) read the spike recorder after every interval.
In PyNEST 3.10, each read of a recorder's `n_events` or `events` copies all events recorded so far.
A diagnostic on 23 October 2026 (Brunel network, 10,000 neurons, 4 threads, Δ = 1 ms, 1000 intervals) measured 1.36 ms per interval for `nest.Run` alone and 9.97 ms with one `n_events` read after each interval.
The per-interval read therefore grew with the run and dominated the `chunked` reference and the NCP arms alike.
The differences O stayed unbiased, but their noise hid the NCP cost for large networks.

This protocol changes only the readback:

- The spike count after each interval comes from the kernel's `local_spike_counter`, the number of spikes in the last `nest.Run`. Its sum equalled the recorder total in the diagnostic (355,693 spikes).
- The new spikes after each interval come from the recorder's ASCII files, one per thread, which NEST flushes after each `nest.Run`. Each read starts at the last complete line of each file. Spike times are recorded in steps of the 0.1 ms resolution, so they are exact integers. In the diagnostic, this read gave exactly the counter's spikes after each of 1000 intervals and cost 1.54 ms per interval in total. With the same seed, the ASCII and the memory records of a 1000-neuron network were identical multisets of (sender, step).
- Each read checks its number of new spikes against the counter, and each run checks the sum against the recorder total once, after the last interval.
- The `-spikes` payloads carry `senders` and `steps` (integers) instead of `senders` and `times` (floating-point milliseconds).

## Changes to the design

- Everything that this file does not change is as in [protocol 1](PROTOCOL.md): networks, arms, parts, timed regions, measures, validity rules, and the treatment of MUSIC with more than one thread.
- The order seed is 20261025. The network seed of block b is still 20261024 + b, so each configuration and block simulates the same network realization as in run 1.
- D4 omits Brunel with 10,000 neurons at Δ = 5 ms. In run 1, all nine NCP runs of that configuration failed closed: the result of some steps exceeded the 65,536-byte frame of the local profile. A diagnostic of the same network found up to 8,112 spikes in one interval and a largest result of 72,151 bytes even with integer steps. The SDK refuses such a result, so this configuration cannot pass with SDK 1.0.x. Delivering large results is a protocol question and is benchmarked separately.

This gives 186 configurations and 558 runs.

## Smoke runs that informed this protocol

On 23 October 2026, smoke runs of the changed harness with one block each gave, for Brunel with 10,000 neurons, 4 threads, and Δ = 1 ms: 2.65 s for `mono`, 2.80 s for `chunked`, and 3.85 s for `ncp-py-1.0.1`. They are not results.

## Hypotheses

H1 to H5 are those of protocol 1, applied to the configurations of this protocol.

- **H6.** For every configuration and block that both runs completed, the recorder total of each arm equals the recorder total of the same configuration and block in run 1.

A hypothesis holds when its criterion holds. Three blocks give no confidence level.
