## Question

Does each coupling deliver exactly the spikes that NEST simulated: the same neurons at the same times?

## Method

For each configuration, [`harness/content.py`](harness/content.py) runs three processes with the same network and seed:

- **reference:** NEST alone runs 2 s in one call, and its spike recorder's complete events are kept;
- **ncp:** the Python host with `ncp_local` 1.0.1 drives the NEST owner with the payload `spikes`, and the host keeps every delivered (neuron, time) pair;
- **music:** NEST sends every spike through MUSIC 1.2.1 to a peer, which keeps every received (channel, time) pair; NEST's own recorder events are kept too.

The comparison uses exact multisets of (neuron, time) pairs, with times rounded to 0.1 µs.
The owner selects the spikes of each interval by time and checks their number against the recorder's count.

## Configurations

Networks `alpha`, `brunel`, and `aeif` of the [campaign protocol](PROTOCOL.md), 1000 neurons, 1, 2, 4, or 8 NEST threads, and Δ of 1 or 5 ms: 24 configurations.
Three blocks run each configuration once, in an order shuffled with the seed 20261025; block b uses the network seed 20261025 + b.

## Earlier observations that set the expectations

Smoke trials on 22 October 2026 found that MUSIC delivered the exact content only with one NEST thread, and that an earlier readback, which took the new events as a slice at the end of the recorder's arrays, was wrong with more than one thread. The readback now selects by time.

## Hypotheses

- **C1.** In every trial, the NCP host receives exactly the reference multiset.
- **C2.** In every trial, NEST's own recorder in the MUSIC run equals the reference multiset.
- **C3.** With one thread, the MUSIC peer receives exactly the recorded multiset in every trial.

A hypothesis holds when its criterion holds. The MUSIC content with more than one thread is reported as observed.
