# NEST campaign: protocol 3

Status: fixed on 23 October 2026, before the recorded runs of this protocol.
Its SHA-256 is in [`PROTOCOL-3.sha256`](PROTOCOL-3.sha256). The schedule records the same digest.
Do not edit this file. Record any deviation in the README.

## Question

What does NCP 2 cost per exchange when it couples NEST 3.10.0 to a host process, compared with NCP 1.0.1 and with MUSIC 1.2.1, under the conditions of protocol 2?

## What is the same as protocol 2

Everything that this file does not change is as in [protocol 2](PROTOCOL-2.md) and [protocol 1](PROTOCOL.md): the computer, the NEST build, the networks, the resolution, the 2 s of simulated time, the readback of constant cost, the parts D1 to D4, the timed regions, the MUSIC arm, and the treatment of MUSIC with more than one thread.
The network seed of block b is 20261024 + b, so each configuration and block simulates the same network realization as in protocols 1 and 2.

## Arms

| Arm | What runs |
| --- | --- |
| `mono`, `chunked`, `chunked-spikes`, `music` | As in protocol 1 |
| `chunked-pipe`, `chunked-pipe-spikes` | As `chunked` and `chunked-spikes`, but after each interval the arm sends the spike count (8 bytes), or the new spikes packed as NCP 2 sends them, to a peer process (`harness/pipe_echo.py`) over a pipe pair and waits for the echo (`harness/pipe_arm.py`). No protocol. |
| `ncp2-py`, `ncp2-py-spikes` | A Python host (`harness/ncp2_host.py`) drives the NEST owner `harness/ncp2_owner.py`, both with the NCP 2 Python SDK of this commit, over a pipe pair. Each step returns the spike count, or the new spikes as a `u32` array of senders and an `i64` array of steps. |
| `ncp2-rs`, `ncp2-rs-spikes` | A Rust host (`harness/ncp2-rust`, NCP 2 Rust SDK of this commit) drives the same owner. |
| `ncp-py-1.0.1`, `ncp-rs-1.0.1`, and their `-spikes` arms | As in protocol 2, with NCP 1.0.1 from a checkout of the tag `sdk-v1.0.1` |

The NCP 2 owner checks the digest of every request, and the NCP 2 hosts check the digest of every response (the default).

This gives 258 configurations and 774 runs.

## Design

Three blocks. Each block runs every configuration once, in an order shuffled with the seed 20261026.
The other rules of protocol 1 apply: the time limit of each run, the record of each run as soon as it ends, the resumption after an interruption, and the load average before each run.
The NCP 1.0.1 Rust host is built from the released SDK with the dependencies in the local cache, as in protocols 1 and 2; the NCP 2 Rust host is built with its `Cargo.lock`.

## Measures

- The NCP cost per exchange, O = (W(NCP arm) − W(`chunked`)) / (2000/Δ), paired within a block; the reference of a `-spikes` arm is `chunked-spikes`.
- The MUSIC cost per run, W(`music`) − W(`mono`), paired within a block, and the same divided by 2000/Δ, to put it on the scale of O.
- Exploratory: the pause cost, (W(`chunked-pipe`) − W(`chunked`)) / (2000/Δ), the cost of stopping after each interval for a round trip to another process; and the protocol cost, (W(NCP arm) − W(`chunked-pipe`)) / (2000/Δ). Their sum is O. The `-spikes` arms pair with `chunked-pipe-spikes` and `chunked-spikes`.

## Validity

As in protocol 1: a run is valid when its process ends with status 0 and, for an NCP arm, the spike count summed at the host equals the recorder total in the owner; within one configuration and block, every arm must record the same number of spikes in NEST's own recorder.

## Smoke runs that informed this protocol

On 23 October 2026, smoke runs of the changed harness gave, for Brunel with 1000 neurons, 1 thread, and Δ = 1 ms, 116,882 spikes in each NCP 2 arm, equal to the recorder total and to protocol 2's total for the same configuration and seed, and costs per exchange from about 0.02 to 0.10 ms with the Rust host and 0.10 to 0.12 ms with the Python host, varying more between runs than between hosts; a pause for a raw round trip after each interval (`chunked-pipe`) cost about 0.015 ms per exchange. For Brunel with 10,000 neurons, 4 threads, and Δ = 5 ms with spikes, the cost was about 0.3 to 0.6 ms per exchange with either host. An NCP 2 call between a Rust client and a Python echo owner takes about 0.02 ms (benchmarks/comparison), so most of these costs come from elsewhere; the `chunked-pipe` arms measure how much comes from pausing NEST for a round trip between processes. The smoke runs also suggest that G3 may not hold for 10,000 neurons. They are not results.

## Hypotheses

- **G1.** D1 with Δ = 1 ms: for each size, thread count, and host language, NCP 2 costs less per exchange than NCP 1.0.1 in every block (12 comparisons).
- **G2.** D1 with Δ = 1 ms: the median of the six median costs per exchange of `ncp2-rs` is at most 0.10 ms (the design target).
- **G3.** D4: each of the four configurations of `ncp2-rs-spikes`, Brunel with 10,000 neurons at Δ = 5 ms included, has a median cost per exchange of at most 0.15 ms (the design target).
- **G4.** Every run is valid, and the recorded spike counts agree across arms within each configuration and block.
- **G5.** The recorder totals equal those of protocol 2 for every configuration and block that both ran.

A hypothesis holds when its criterion holds. Three blocks give no confidence level.
No hypothesis compares NCP with MUSIC: protocol 2 found MUSIC cheaper per run than NCP 1.0.1, and NCP 2 still makes one round trip between processes for each exchange. The comparison is reported as measured.

## Not claimed

No real-time or worst-case bound. No measurement between computers. No claim about other simulators, MUSIC versions, or network models.
The timing of MUSIC runs with more than one NEST thread measures a coupling that does not deliver the correct spikes in this build (protocol 1).
