## Question

How does the cost of coupling NEST to a peer process change with the network, the neuron model, the network size, the number of NEST threads, the exchange interval, the payload, the NCP SDK version, and the host language?
How does it compare with MUSIC under the same conditions?

## Earlier results that set the thresholds

- The preregistered coupling benchmark of 13 October 2026 measured an NCP exchange cost of about 1.5 ms with the Python SDK 1.0.0, on one network of 1000 alpha neurons with one thread.
- Protocol 2 of the local SDK exchange benchmark measured a Python lockstep call of 504 µs with SDK 1.0.1 and an echo owner, and 227 µs for a Rust client with a Python owner.
- Calibration runs on 22 October 2026 set the drive of the adaptive network. They are not results.

## Networks

Every connection delay equals the exchange interval Δ, so the minimum delay of NEST and the MUSIC tick both equal Δ.
The resolution is 0.1 ms. The simulated time is 2 s per run.

| Name | Neurons | Input | Recurrent connections |
| --- | --- | --- | --- |
| `alpha` | `iaf_psc_alpha`, default parameters | One Poisson generator each, 6000 Hz, 10.4 pA | 100 per neuron, 2.0 pA |
| `brunel` | `iaf_psc_delta`, 80 % excitatory, Brunel (2000) model A parameters | One shared Poisson generator at η = 2 | Probability 0.1 as fixed indegree, J = 0.1 mV, g = 5 |
| `aeif` | `aeif_cond_exp`, default parameters, 80 % excitatory | One Poisson generator each, 7000 Hz, 10 nS | 80 excitatory (1 nS) and 20 inhibitory (−4 nS) per neuron |

## Arms

| Arm | What runs | Timed region |
| --- | --- | --- |
| `mono` | One `nest.Run(2000 ms)` | The run |
| `chunked` | `nest.Run(Δ)` 2000/Δ times; the spike count is read after each | All intervals |
| `chunked-spikes` | The same; the new spikes are read after each | All intervals |
| `ncp-py-1.0.0`, `ncp-py-1.0.1` | A Python host drives a Python NEST owner with `ncp_local` 1.0.0 or 1.0.1; each step returns the spike count | All steps, at the host |
| `ncp-rs-1.0.1` | A Rust host with `ncp-local` 1.0.1 drives the Python NEST owner with 1.0.1 | All steps, at the host |
| `-spikes` variants of the NCP arms | Each step returns the new spikes | All steps, at the host |
| `music` | `mpiexec` starts NEST and a peer with MUSIC 1.2.1; NEST sends every spike, and the peer returns one event per tick | The run |

Starting processes, building the network, and `nest.Prepare` are outside the timed region.

## Design

Three blocks run back to back. Each block runs every configuration once, in an order shuffled with the seed 20261024.
All arms of one block use the same network seed: 20261024 plus the block number. The three blocks therefore use three network realizations.
The computer is in normal use with other programs. The runner records the one-minute load average before each run.
Each run has a limit of 30 minutes. The runner appends each finished run to a file and syncs it, and it resumes after an interruption.

## Validity

- A run is valid when its process ends with status 0 and, for NCP arms, the spike count summed at the host equals the recorder total in the owner.
- Within one configuration of one block, every arm must record the same number of spikes in NEST's own spike recorder.
- For `music` with one NEST thread, the peer must receive exactly the number of spikes that NEST recorded.

## A MUSIC finding before this protocol

Smoke runs on 22 October 2026 found that, in this build, the MUSIC event stream from NEST is correct only with one NEST thread.
With T threads, only n/T of n peer channels carried the exact spike train of their neuron (500, 250, and 125 of 1000 for T = 2, 4, and 8), and the totals differed by up to 167 events.
NEST's own recorder gave the same counts as the other arms. The per-neuron connection form and the single-call channel-list form gave the same result.
`music-threads/` holds the reproduction. For `music` with more than one thread, the campaign therefore records the delivered count next to the recorded count and does not require them to agree.
The timing of those runs measures a coupling that does not deliver correct content; the README states this wherever it reports them.

## Measures

- Wall time W of each run.
- The NCP cost per exchange, O = (W(NCP arm) − W(`chunked`)) / (2000/Δ), paired within a block; for `-spikes` arms the reference is `chunked-spikes`.
- The MUSIC cost per run, W(`music`) − W(`mono`), paired within a block.
- The real-time factor, W / 2 s.

## Hypotheses

- **H1.** D1 with Δ = 1 ms: for each size and thread count, the median O of `ncp-py-1.0.1` is lower than the median O of `ncp-py-1.0.0`.
- **H2.** D1: the median O of `ncp-py-1.0.1` over all 18 configurations is at most 0.6 ms.
- **H3.** D1: for each configuration, the median O of `ncp-rs-1.0.1` is lower than the median O of `ncp-py-1.0.1`.
- **H4.** D3: the median O of `ncp-py-1.0.1` with 25000 neurons is at most twice the median O with 250 neurons.
- **H5.** Every run is valid, and NEST's recorded spike counts agree across arms within each configuration and block.

A hypothesis holds when its criterion holds. Three blocks give no confidence level.

## Not claimed

No real-time or worst-case bound. No measurement between computers. No claim about other simulators, MUSIC versions, or network models.
