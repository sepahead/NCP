# Pipelined acknowledgement: protocol

## Question

The v1 local profile requires that only a verified acknowledgement advances the client's sequence.
A lockstep call therefore needs two round trips: one for the request and one for the acknowledgement.
A pipelined client sends acknowledgement n and request n+1 back to back, so a call needs one round trip.

1. Is a pipelined client safe against the unchanged v1 owner?
2. How much time per call does pipelining save with SDK 1.0.1?

Pipelining is not part of the v1 profile. A pipelined client needs a new profile identity before any use.

## Safety analysis

[`model/model_check.py`](model/model_check.py) explores every interleaving of client steps, owner steps, and faults for three clients:
the v1 sequential client, a v1-compliant deferred client, and the pipelined client.
The faults are frame corruption, a valid but wrong acknowledgement, owner crash, client crash, and client timeout.
It checks six properties in every reachable state: at-most-once execution (P1), execution order (P2), an accepted acknowledgement of the predecessor before each execution (P3), true committed records (P4), true not-executed records (P5), and the v1 client rule (P6).

Required results:

- The sequential and the deferred client violate no property with 4 steps and 2 faults, and with 3 steps and 3 faults.
- The pipelined client violates only P6.
- The mutation self-test detects each deliberate defect with the expected property.
- [`model/conformance.py`](model/conformance.py) finds no difference between the model's owner and the real Python `LocalOwner` on 20,000 random traces.

If one of these fails, no timed run starts.

## Configurations

Every configuration uses SDK 1.0.1 and an echo owner.

| Name | Client | Owner | Spikes per step |
| --- | --- | --- | --- |
| `rust-rust-{sequential,pipelined}-n{0,127}` | Rust | Rust | 0, 127 |
| `rust-python-{sequential,pipelined}-n{0,127}` | Rust | Python | 0, 127 |
| `python-python-{sdk,sequential,pipelined}-n{0,127}` | Python | Python | 0, 127 |
| `python-rust-{sdk,sequential,pipelined}-n{0,127}` | Python | Rust | 0, 127 |

`sdk` uses `LocalClient.call`. `sequential` and `pipelined` use the same public functions, so only the order of frames differs.

## Design

Three blocks run back to back. Each block contains every configuration once, in an order shuffled with the seed 20261023.
Each run sends `prepare`, 500 warm-up calls, 3000 timed calls, and `finish`.
The runner appends each finished run to a file and syncs it, and it resumes after an interruption without repeating finished runs.
The computer is in normal use with other programs. The runner records the one-minute load average before each run.

## Measures

For each run: the median and the 5th, 95th, and 99th percentiles of the call times.
For each pair of sequential and pipelined configurations with the same client, owner, and spikes: in each block, the sequential run median divided by the pipelined run median, and their difference.

## Hypotheses

- **H1.** Rust client and Rust owner without spikes: the pipelined run median is lower than the sequential run median in each block.
- **H2.** Python client and Python owner without spikes: the pipelined run median is lower than the sequential run median in each block.
- **H3.** Rust client and Rust owner without spikes: the median difference between sequential and pipelined is at least 3 µs.

A hypothesis holds when its criterion holds. Three blocks give no confidence level.

## Not claimed

No decision to adopt pipelining. No real-time or worst-case bound. No measurement with a simulation owner.
