# Local SDK exchange benchmark: protocol 2, SDK 1.0.1

Status: fixed on 22 October 2026, before the recorded runs of protocol 2.
Its SHA-256 is in [`PROTOCOL-2.sha256`](PROTOCOL-2.sha256). The run records the same digest.
Do not edit this file. Record any deviation in the README.

## Question

How much faster is one lockstep call with the local SDK 1.0.1 than with the released SDK 1.0.0, in Rust, in Python, and across the two languages?

The call, workload, measures, and limits are those of [protocol 1](PROTOCOL.md).
Protocol 2 adds the released and the current Python SDK as separate sources and a Python transcript check.

## Earlier results that set the thresholds

- Protocol 1 measured a Rust change that did less than 1.0.1: the median paired ratio was 7.4 without spikes and 5.0 with 127 spikes.
- An interleaved measurement of the Python change, outside any protocol, gave paired ratios of 3.04 without spikes, 3.03 with 13 spikes, and 3.15 with 127 spikes.

## Sources

- **Released:** `local/rust` and `local/python` from the tag `sdk-v1.0.0`.
- **Current:** `local/rust` and `local/python` of this checkout, version 1.0.1.

## Validity checks

1. The released and the current Rust owner print the same transcript for the fixed script of protocol 1.
2. The released and the current Python SDK print the same transcript for a fixed script ([`harness/python/transcript.py`](harness/python/transcript.py)).
   The script records every request byte string, every owner output, and every `LocalClient` frame over real pipes.
   It covers valid steps, retries, result lookups, wrong and repeated acknowledgements, a role violation, a foreign run, a sequence gap, a backend failure, a rejected body, an oversized request, and a bad sequence number.
3. If either pair of transcripts differs, no timed run starts.
4. The per-run checks of protocol 1 apply.

## Configurations

Each pair runs with the released and with the current sources. Client and owner use the same source in each run.

| Name | Client | Owner | Spikes per step |
| --- | --- | --- | --- |
| `rust-rust-{released,current}-n{0,13,127,500}` | Rust | Rust | 0, 13, 127, 500 |
| `python-python-{released,current}-n{0,13,127}` | Python | Python | 0, 13, 127 |
| `python-rust-{released,current}-n{0,127}` | Python | Rust | 0, 127 |
| `rust-python-{released,current}-n{0,127}` | Rust | Python | 0, 127 |
| `phases-{released,current}-n{0,127}` | Rust, in one process | | 0, 127 |
| `raw-rust`, `raw-python` | Framed echo of 512 bytes without NCP | | none |

## Design and measures

As in protocol 1: five rounds, every configuration once per round in an order shuffled with the seed 20261022, 500 warm-up calls and 3000 timed calls per run.
The paired ratio of a configuration is, in each round, the released run median divided by the current run median.

## Hypotheses

- **H1.** Rust client and Rust owner without spikes: the median paired ratio is at least 6.
- **H2.** Python client and Python owner without spikes: the median paired ratio is at least 2.5.
- **H3.** Python client and Python owner with 127 spikes: the median paired ratio is at least 2.5.
- **H4.** For each of the eleven paired configurations, the current run median is lower than the released run median in each of the five rounds.

A hypothesis holds when its criterion holds. Five rounds give no confidence level, so no significance test is used.

## Not claimed

No real-time bound, no worst-case bound, and no ranking against another protocol.
The benchmark does not measure an owner that does simulation work.
