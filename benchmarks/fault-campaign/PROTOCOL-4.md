# Fault campaign: protocol 4, for NCP 2 over sockets and with the Rust client

Status: fixed on 3 November 2026, before the recorded trials of this protocol.
Its SHA-256 is in [`PROTOCOL-4.sha256`](PROTOCOL-4.sha256). The schedule records the same digest.
Do not edit this file. Record any deviation in the README.

## Question

Do the results of [protocol 3](PROTOCOL-3.md) hold when client and owner talk over a Unix domain socket or TCP, and when the client is the Rust SDK?
Protocols 2 and 3 used pipes and the Python client only (protocol 2, "What the results do not show").

## What is new

- **Bindings.** A Unix domain socket, and TCP on the loopback interface. The owner runs as a server and serves one session for each connection: the Python owner of protocol 3 as a server ([`harness/fault_owner4.py`](harness/fault_owner4.py)), or the Rust echo owner of `rust/examples` in its `unix PATH` and `tcp` modes. Each owner appends the body of each execution to the execution log before it runs, as in protocol 3.
- **Relay.** [`harness/relay_socket.py`](harness/relay_socket.py) makes the changes of `relay2.py` between client and owner over sockets. Where `relay2.py` closes a pipe, it shuts down the writing side of the socket.
- **Clients.** The NCP 2 Python client, in the trial's process as in protocol 3, and a Rust client ([`harness/rust-client`](harness/rust-client/src/main.rs)) that runs the same session and reports the same views. Both have a receive time limit of 2 s: the Rust client sets it with `set_unix_timeout` or `set_tcp_timeout` (NCP commits `01e57cd` and `a320afe`).
- **Killed clients.** A server does not exit when one of its clients dies. The trial checks instead that the owner serves a new session, with one step, within 10 s.
- **Killed owners.** The driver ([`harness/fault_client4.py`](harness/fault_client4.py)) starts the timer that kills the owner once the client is connected: at a random time from 0 to 0.2 s for the Python owner, whose steps sleep 20 ms each, and from 0 to 5 ms for the Rust owner.

## What is the same as protocol 3

The scenarios other than the soaks, the session (open, six steps k = 1 to 6, and close, with spikes at k = 2, 4, and 6), the draws from each trial's seed, the execution log, the views, the three invariants (once, in order, known), and the criteria of E1 to E5, E7, and E8.

Each scenario runs with both bindings and both clients. A block has 1,520 trials: 200 for each binding and client with the Python owner, and 180 with the Rust owner. Three blocks give 4,560 trials. [`run4.py`](run4.py) shuffles each block with the seed 20261105, appends each trial to `trials.jsonl`, and resumes after an interruption.

The trials measure no time except the detection of a stall, so they need no controlled conditions, as in protocols 2 and 3. The computer may run on battery; the schedule records the power source.

## Hypotheses

- **E1.** No trial accepts a wrong result.
- **E2.** In every trial, the owner executes each step at most once, in order (invariants 1 and 2).
- **E3.** In every trial, what the client learned is true (invariant 3).
- **E4.** Every failure reaches the application as an error that the client's SDK documents for a call: `Rejected`, `Ended`, or `ProtocolError` in Python, and `Error::Rejected`, `Error::Ended`, or `Error::Protocol` in Rust.
- **E5.** Every flipped or truncated frame ends the session before it completes.
- **E6.** After every killed client, the owner serves a new session within 10 s.
- **E7.** Every stall ends with the code `timeout` and executed `unknown` within 3 s of the start of the session.
- **E8.** An oversized result ends with `result_too_large` and executed `yes`; a raising handler ends with `owner_failure` and executed `unknown`; an oversized request is refused before it is sent, and the session then completes.

A hypothesis holds when its criterion holds in every combination of binding, client, and owner, and every scheduled trial ran. Three blocks give no confidence level. [`analyze4.py`](analyze4.py) applies the criteria.

## What the results do not show

- One computer and one operating system, macOS, and TCP only on the loopback interface: no network, and no lost frames, which are the domain of the planned Zenoh binding.
- A relay that changes frames stands for damage that the transport does not catch. TCP and Unix domain sockets do not damage or repeat frames by themselves.
- No soaks over sockets: the soaks of protocol 3 used pipes.
- The Rust client over pipes (`spawn`) is not part of the trials, because a pipe takes no time limit in the Rust SDK; a corrupted length can then leave it waiting. `spawn_unix` gives a child owner a socket pair instead, and its client code is the code that the trials over Unix domain sockets exercise.
- One session at a time for each owner. The [multi-agent benchmark](../multi-agent/README.md) runs many sessions at once, without faults.

## Smoke runs that informed this protocol

On 3 November 2026, before this protocol was fixed, single trials of every scenario with each combination of binding, client, and owner found one defect of the new Rust client, corrected before the smoke run: it reported an error at `close` by its view instead of the name of its error.
While the harness was written, a Rust client over pipes would have waited forever for the rest of a frame whose length a flip had made larger; this led to `spawn_unix` and `set_unix_timeout` in the Rust SDK, and to leaving pipes out of these trials.
A smoke run of the runner with one trial of each of the 88 combinations of scenario, owner, binding, and client ran every trial, and every criterion held. Its flipped bits fell into the JSON region (12), the attachments (2), and the digest (2).
