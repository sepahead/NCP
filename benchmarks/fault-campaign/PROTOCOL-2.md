# Fault campaign: protocol 2, for NCP 2

Status: fixed on 2 November 2026, before the recorded trials.
Its SHA-256 is in [`PROTOCOL-2.sha256`](PROTOCOL-2.sha256). The schedule records the same digest.
Do not edit this file. Record any deviation in the README.

## Question

What happens when an NCP 2 session meets each failure that the specification names?
Does any failure make a client accept a wrong result, make an owner execute a request twice or out of order, or make a client believe something false about a request?

## Why a second protocol

[Protocol 1](PROTOCOL.md) tested NCP 1.0.1.
NCP 2 has other rules: the receipt in the next request, the kept response, the outcome classes, and the possibly executed request.
The Lean proofs cover the owner's rules for every sequence of requests, and the model check covers bounded runs with faults.
This protocol tests the two SDKs as real processes, with real pipes and real kills.

## Trials

Every trial uses the NCP 2 Python client of the commit that the schedule records, with a time limit of 2 s and a session bound of 65,536 bytes.
A trial is one session: `open`, six steps k = 1 to 6, and `close`. Steps 2, 4, and 6 call `spikes` with 127, 1788, and 127 spikes; the others call `echo` with a small body that contains k.
The client checks every result that it accepts: an echo must equal its request, and the arrays of `spikes` must equal the generator's.
The owner is [`harness/fault_owner2.py`](harness/fault_owner2.py), with the NCP 2 Python SDK, or the Rust echo owner `rust/examples/echo_owner.rs`. Before it executes a request, each owner appends the request body to an execution log, in one write.

| Scenario | What happens | Owners |
| --- | --- | --- |
| `flip-c2o`, `flip-o2c` | A relay ([`harness/relay2.py`](harness/relay2.py)) flips one random bit of one random frame, anywhere in it, from the client or from the owner | Python, Rust |
| `truncate-c2o`, `truncate-o2c` | The relay forwards a random proper prefix of one random frame and closes that direction | Python, Rust |
| `duplicate-c2o`, `duplicate-o2c` | The relay forwards one random frame twice | Python, Rust |
| `kill-owner` | The client's process kills the owner with SIGKILL at a random time from 0 to 0.2 s (Python, whose executions sleep 20 ms each) or from 0 to 5 ms (Rust) | Python, Rust |
| `kill-client` | The trial kills a running client with SIGKILL at a random time from 0 to 0.1 s; its owner must exit | Python, Rust |
| `stall` | One step sleeps three times the client's time limit | Python |
| `oversize-response` | One step returns a result larger than the session bound | Python |
| `oversize-request` | The client tries one request larger than the session bound, then sends the step | Python, Rust |
| `backend-raise` | One step calls `fail`, whose handler raises | Python, Rust |
| `soak` | One long session, with the resident memory and the open descriptors of client and owner sampled every 0.5 s ([`harness/soak2.py`](harness/soak2.py)): the Python client with the Python owner, 200,000 calls; the Python client with the Rust owner, 1,000,000 calls; and the Rust client `rust/examples/bench_client` with the Rust owner, 1,000,000 calls, keeping one call time in 1000 | As stated |

## Design

Three blocks. Each block runs every trial of the plan once, in an order shuffled with the seed 20261103.
Per block, the plan has 200 trials of each `flip` scenario and owner, 60 of each `truncate` scenario and owner, 30 of each `duplicate` scenario and owner, 40 of `kill-owner` and 20 of `kill-client` per owner, 10 of `stall`, 20 of `oversize-response`, 20 of `oversize-request` and of `backend-raise` per owner, and one soak of each kind.
This gives 4,170 trials and 9 soaks.
The runner is [`run2.py`](run2.py); it appends each trial to a file, syncs it, and resumes after an interruption. The analysis is [`analyze2.py`](analyze2.py).
Only the detection time of a stall is a time measure, so the trials do not need the controlled conditions of the benchmarks.

## What the client learned

For each step k that it sent, the client records one view:
`ok` (accepted, and the result is right), `wrong` (accepted, but the result is wrong), `rejected:CODE`, `ended:CODE:EXECUTED`, where EXECUTED is `yes`, `no`, or `unknown`, or `protocol_error`.
Each trial checks three invariants against the owner's execution log:

1. **Once.** No step appears twice in the log.
2. **In order.** The log holds the steps 1, 2, ..., m, in this order.
3. **Known.** Every step that the client saw as `ok`, `wrong`, or executed `yes` is in the log. No step that the client saw rejected, except with `seq_stale`, or executed `no` is in the log. At most one step is uncertain, that is, executed `unknown` or a protocol error, and it is the last step that the client sent. Every step in the log is known to the client as executed, or is the uncertain step.

## Hypotheses

- **E1.** No trial accepts a wrong result.
- **E2.** In every trial, the owner executes each step at most once, in order (invariants 1 and 2).
- **E3.** In every trial, what the client learned is true (invariant 3).
- **E4.** Every failure reaches the application as `Rejected`, `Ended`, or `ProtocolError`, the exceptions that the Python SDK documents.
- **E5.** Every flipped or truncated frame ends the session before it completes.
- **E6.** Every killed client leaves its owner exited within 10 s.
- **E7.** Every stall ends with the code `timeout` and executed `unknown` within 3 s of the start of the session.
- **E8.** An oversized result ends with `result_too_large` and executed `yes`; a raising handler ends with `owner_failure` and executed `unknown`; an oversized request is refused before it is sent, and the session then completes.
- **E9.** In each soak, every call returns the right result, the resident memory of client and owner grows by less than 10 % after the first tenth of the soak, and the open descriptors of each stay constant after the first tenth.

A hypothesis holds when its criterion holds and every scheduled trial ran. Three blocks give no confidence level.

## Smoke runs that informed this protocol

On 2 November 2026, before this protocol was fixed, the runner ran one trial of each scenario and owner, and three soaks of 20,000 calls, at the commit `c24ff2f` with the changes of this protocol in the worktree.
Every trial ran. No trial accepted a wrong result, and every invariant held.
Of the flipped frames, three bits were in the JSON region and one in the attachments.
The soaks were too short for ten samples. The soak of the Rust client took 3.4 s instead of about 0.6 s: for about 3 s, its client had 32 KB of resident memory and no owner yet. Run again directly, the same soak took 0.63 s. The first start of a new binary can be slow on macOS, so `run2.py` runs each built binary once before the trials.
These runs are not results.

## What the results do not show

- The fault trials use the Python client. The Rust client is covered by the soak, by the tests in `rust/tests`, and by the model conformance of the gate.
- One computer and one operating system, and the byte-stream binding over pipes only, not Unix domain sockets or TCP.
- A relay that changes frames stands for damage on the way. A byte stream does not repeat frames by itself: the duplicate scenarios test only that a repeated frame executes nothing twice and leaves the client with true knowledge.
