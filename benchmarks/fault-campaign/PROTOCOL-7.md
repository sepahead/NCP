# Fault campaign: protocol 7, NCP 2 revision 7 over the Zenoh binding

Status: fixed on 18 November 2026, before the recorded trials of this protocol.
Its SHA-256 is in [`PROTOCOL-7.sha256`](PROTOCOL-7.sha256). The schedule records the same digest.
Do not edit this file. Record any deviation in the README.

## Why a seventh protocol

Protocols 2 to 6 ran over pipes, Unix domain sockets, and TCP, which deliver each frame once and in order. There, the kept response, the repeat of a request after a time limit, and the rules for a lost session never act.
The Zenoh binding (specification section 9.2) runs over a network that can lose, repeat, delay, and replay a message, and its owners can die and restart; its client therefore sends a request again after its time limit, and an owner answers a repeat with its kept response.
The binding's tests cover one lost query, one lost reply, an expired session, and a restart. The release record lists a fault campaign on the Zenoh binding, with owner restarts, delayed and repeated `open`, and replayed frames, as NOT RUN.

## Design

[`harness/zenoh_fault7.py`](harness/zenoh_fault7.py) runs one trial: one session of `open`, six `echo` steps, and `close` (eight requests, seq 0 to 7) between the NCP 2 Python client of revision 7 and an owner in its own process: the Python Zenoh echo owner of the binding's tests or the Rust example `zenoh_echo_owner`, each of which logs every execution before it runs. Client and owner are Zenoh peers on one TCP endpoint of the loopback interface.
The client's time limit is 0.5 s, and it sends a request again up to 10 times. Its channel applies the faults of a plan drawn from the trial's seed, each to the first sending of one request, chosen by its seq:

| Scenario | Fault |
| --- | --- |
| `drop-query` | The query never leaves the client. |
| `drop-reply` | The reply never reaches the client. |
| `duplicate-query` | The query leaves twice. |
| `delay-reply` | The reply reaches the client only after its time limit, behind the reply to the repeat. |
| `replay-request` | After the first sending of request k, the frame of an earlier request j leaves again. |
| `replay-open` | The same with j = 0: a delayed copy of `open`. |
| `two-faults` | Two different faults of the six above, on two different requests. |
| `restart-owner` | The owner process is killed just before or just after the first sending of request k, and started again with the same service before the client sends anything more. |
| `kill-owner` | The same, and the owner is not started again. |

[`run7.py`](run7.py) runs three blocks. Each block holds, for each owner, 20 trials of each of the first seven scenarios and 10 of each of the last two: 320 trials, 960 in all. The order of each block is shuffled with the seed 20261119. [`analyze7.py`](analyze7.py) applies the criteria.
The views of the client, the execution log, and the invariants are those of protocol 6 ([`harness/fault_client6.py`](harness/fault_client6.py)). The trials time nothing except the client's own time limits, so they need no controlled conditions.

## Hypotheses

| # | Hypothesis |
| --- | --- |
| E1 | No trial accepts a wrong result. |
| E2 | In every trial, the owner executes each step at most once, in order. |
| E3 | In every trial, what the client learned about each step is true, and at most one step is uncertain. |
| E4 | Every failure reaches the application as an error that the client's SDK documents for a call. |
| Z1 | Every trial with faults of the network only (the first seven scenarios) completes, with every fault applied. |
| Z2 | Every trial with a killed owner that is not started again ends early. |

A hypothesis holds only if every scheduled trial ran.

## What the results do not show

One computer, the loopback interface, one client and one owner at a time, Zenoh 1.10.2 in peer mode without a router, and faults that the client's channel injects at the frame level, not by Zenoh's own transport. The Rust client of the binding is not part of this protocol; the binding's tests cover it. The trials say nothing about performance.

## Smoke trials that informed this protocol

On 18 November 2026, before this protocol was fixed, single trials of each scenario ran with both owners.
In the first version of the harness, the owner was killed at a random time after the start of the session; a session took about 10 ms, so the kill came after its end, and the session completed. The kill is now tied to the first sending of a request.
With that change: after `restart-owner`, the request of the lost session got `session_expired`, possibly executed, and the execution log agreed; after `kill-owner`, the client ended with `local.timeout`, possibly executed, after about 5.5 s; each network fault was applied, and the session completed with each step once.
The plan of `two-faults` could put both faults on one request, where a dropped query hides a duplicated one; the two faults now fall on two requests.
A smoke run of `run7.py --smoke`, one trial of each scenario with each owner, then ran all 18 trials, and every criterion held.
These trials are not results.
