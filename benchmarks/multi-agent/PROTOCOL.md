# Multi-agent benchmark: protocol

This protocol was fixed on 3 November 2026, before its timed runs. Its SHA-256 digest is in [`PROTOCOL.sha256`](PROTOCOL.sha256), and the schedule records the same digest.
Do not edit this file. Record any deviation in the README.

## 1. Questions

NCP 2 couples one program with many others in three ways ([specification](../../spec/NCP-2.md), section 16, and the [rounds profile](../../spec/NCP-2-ROUNDS.md)):

1. **One host, many owners (part F).** A host, such as the controller of many agents, sends one request to each of N owners and waits for all responses. How does the time of such a round grow with N, with a Rust and with a Python host? Is `call_all`, which sends every request before it reads the first response, faster than one thread for each session and than one call after another? Do threads that each use `call_all` on a share of the sessions help? What does NCP 2 add to the same round over plain pipes?
2. **Many agents, one owner, in rounds (part R).** N agents share one owner, such as a simulated world, that applies one request of each agent per round, in the order of the members. Do all agents agree on every round, and does the world's state stay the same whatever the order in which the requests arrive? What does the profile cost, compared with an owner that applies each request when it arrives?
3. **The rank-0 owner of an MPI program (part M).** An owner that is an MPI program with R processes (ranks) serves one session from rank 0. Does the client receive exactly the data of all ranks, and what does the pattern add to a call?

## 2. Computer and software

- Apple MacBook Pro (Mac16,5) with an Apple M4 Max: 16 cores, of which 12 are performance cores, and 128 GB of memory; macOS 26.5.1; on its power adapter.
- Rust 1.99.1. The harness pins its dependencies in [`harness/rust/Cargo.lock`](harness/rust/Cargo.lock), the same versions as the NCP 2 Rust SDK.
- Python 3.15.0 for the Python programs of parts F and R. The NCP 2 Python SDK uses only the standard library.
- For part M, the conda environment of the NEST 3.10.0 build: Python 3.11.15, Open MPI 5.0.10, mpi4py 4.1.2, and numpy 1.26.4.
- The NCP 2 SDKs at the commit that the schedule records.

## 3. Programs

- [`harness/rust`](harness/rust/src/main.rs), one program with five roles:
  - `owner W`: an NCP 2 owner on its standard input and output. Each `echo` request waits W microseconds (a sleep of the thread) and returns its body.
  - `raw-owner W`: the same without a protocol. It reads a 4-byte little-endian length and that many bytes, waits W microseconds, and writes them back.
  - `fanout`: part F with a Rust host. `agents`: the agents of part R. `spikes`: the client of part M.
- [`harness/python/fanout.py`](harness/python/fanout.py): part F with a Python host.
- [`harness/python/world_owner.py`](harness/python/world_owner.py): the owner of part R.
- [`harness/python/mpi_owner.py`](harness/python/mpi_owner.py): the owner of part M.

## 4. Configurations and measures

### Part F: one host, N owners

The host starts N owner processes and opens one session with each over a pipe pair.
A round sends one request to each owner, with the body `{"round": r, "agent": i}`, and ends when the last response has arrived.
The time of a round runs from just before the first request is sent until the last response has been received. The host checks every response after the time is taken; a wrong response fails the run.

| Factor | Values |
| --- | --- |
| Host | Rust, Python |
| Mode | `all`: `call_all` of the host's SDK. `pool`: one thread for each session for the whole run (Rust: N threads and two barriers for each round; Python: a `ThreadPoolExecutor` with N workers), each thread calling its session. `split`: min(N, 8) threads for the whole run, each with a contiguous share of the sessions, on which it uses `call_all` (a thread with one session calls it); 8 is half of the 16 cores, which leaves the other half to the owners. `sequential`: one call after another. `raw`: N `raw-owner` processes and the same bodies as JSON bytes, every message written before the first response is read. |
| N | 1, 4, 16, 64, 256 |
| W | 0 and 1000 µs |

That makes 100 configurations. Each run has 20 warm-up rounds and then 200 measured rounds. The measure of a run is the median of its 200 round times.

### Part R: N agents, one owner

The owner `world_owner.py MODE PATH N` runs with Python 3.15.0. It serves the sessions of the agents `agent-000` to `agent-(N-1)` on a Unix domain socket, each session in its own thread (`ncp.UnixServer`). Its state starts as 32 zero bytes.

- `rounds`: `ncp.Rounds` with the N members and a deadline of 60 s. The step of a round sets the state to the SHA-256 digest of the state followed by the compact JSON text of `[[agent, action], ...]`, in member order. Every agent receives `{"state": ...}`, the state after the round in hexadecimal, with the record of the round.
- `arrival`: each request is applied when its thread takes the world's lock: the state becomes the SHA-256 digest of the state followed by the compact JSON text of `[agent, action]`. The agent receives the state after its own action.

The agents are N threads of one process (`agents`). Their sessions open one after another, before the measured rounds. Before each round, all agents wait at a barrier; then each agent sends one request whose action is `[i, k]` for agent i in round k. In `rounds` mode the request carries `"ncp.round": {"agent": "agent-i", "round": k}`, and the agent checks the record of each response as client rule 1 of the profile requires, together with the round number and the dtype and shape of the array; a failed check fails the run. In `arrival` mode, the agent and the round are plain members of the body.
Agent 0 takes the time of each round, from the barrier that starts it to the barrier that starts the next round.
At the end, the owner reports its final state and, in `rounds` mode, the excluded members and the number of rounds in which the requests passed validation in an order other than the member order. A request is recorded just after its validation, so this order is close to, but not exactly, the order of arrival.

| Factor | Values |
| --- | --- |
| Mode | `rounds`, `arrival` |
| N | 1, 4, 16, 64, 256 |

That makes 10 configurations. Each run has 20 warm-up rounds and then 200 measured rounds; the measure of a run is the median of its 200 round times.

### Part M: the rank-0 owner

The owner runs as `mpirun -n R python mpi_owner.py PATH` in the MPI environment, or, for R = 0, as `python mpi_owner.py PATH --no-mpi` without MPI. Rank 0 serves one session on a Unix domain socket, with a session bound of 4 MiB.
For each `spikes` request `{"n": S}`, rank 0 sends S to every rank with an MPI broadcast. Each rank makes its share of the S spikes: S divided by R, and one more for the first (S mod R) ranks. Rank 0 collects the shares in rank order with two MPI gathers, one for the senders (u32) and one for the times (f64), and responds with both arrays. Without MPI, the one process makes all S spikes.
Spike i of a call comes from sender (i mod 1000) + 1 at time (i mod 100) / 10 + 0.1 ms, whichever rank made it. The client (`spikes`, Rust) times each call from just before the request is sent until the response is received and its digest checked, and then compares every spike, bit for bit; a mismatch fails the run.

| Factor | Values |
| --- | --- |
| R | 0 (no MPI), 1, 2, 4, 8 |
| S | 0; 1788 (21 KiB); 87381 (1 MiB) |

That makes 15 configurations. Runs with S of 0 or 1788 have 100 warm-up calls and then 2000 measured calls; runs with S = 87381 have 30 and then 300. The measure of a run is the median call time.

## 5. Design

The 125 configurations each run once in each of three blocks. Within a block, the order is shuffled with the seed 20261103 ([`run.py`](run.py)). The runner appends each finished run to `runs.jsonl` and syncs it to disk; a later call resumes after the last recorded run.

## 6. Conditions

Before each run, the runner waits until all of these hold ([`../conditions.py`](../conditions.py), the rules of NEST protocol 5 and comparison protocol 2):

- the computer draws power from its adapter;
- its thermal pressure level is 0, nominal;
- a core runs at 4.0 GHz or more (the clock probe of the NEST campaign);
- the one-minute load average is below 8.

A run is disturbed when the computer slept for more than 0.5 s during it, or when at its end the computer ran on battery, had a thermal pressure level other than 0, or ran below 3.8 GHz.
The runner repeats a disturbed run at once, at most three times in all. The analysis uses the last attempt. A run that is still disturbed after three attempts is reported and left out of the statistics.

## 7. Validity checks

Before any timed run, `run.py` runs these checks and records them in `validity.json`. If one fails, no timed run starts.

- The Python SDK tests (`test_ncp.py`, `test_rounds.py`) with Python 3.15.0, and the Rust SDK tests.
- The MPI environment imports mpi4py, numpy, and the NCP 2 Python SDK.
- One short run of each of five configurations: part F with `all`, N = 4, and W = 0 for each host; part R with N = 4 in both modes; and part M with 2 ranks and 1788 spikes.

## 8. Exclusions and repeats

A run that fails, because a program exits with an error, a check fails, or a time limit passes, is recorded and repeated once after all scheduled runs. If the repeat fails too, the configuration has no result for that block, and the report says so.
No run is excluded for its timing.

## 9. Statistics

The statistic of a configuration is the median of its block measures, normally three. Its range runs from the smallest to the largest block measure. The hypotheses compare statistics unless they say otherwise. A hypothesis that needs a configuration without any result does not hold.

## 10. Hypotheses

The pilot runs of section 12 suggested these hypotheses.

| # | Hypothesis | Decision rule |
| --- | --- | --- |
| F1 | One host serves 64 owners that answer at once within one millisecond. | W = 0, mode `all`, N = 64: the statistic is below 1000 µs, with the Rust host and with the Python host. |
| F2 | With `call_all`, owners that wait do their waiting at the same time. | W = 1000 µs, N = 64: the statistic of `all` is below one tenth of the statistic of `sequential`, with both hosts. |
| F3 | Sending every request before reading the first response is faster than one thread for each session and than one call after another. | W = 0; N = 4, 16, 64, and 256; both hosts: the statistic of `all` is below the statistic of `pool` and below the statistic of `sequential` (16 comparisons). |
| F4 | What NCP 2 adds to each session falls as sessions are added, because their calls overlap. | W = 0, both hosts: (statistic of `all` − statistic of `raw`) / 256 at N = 256 is below (statistic of `all` − statistic of `raw`) at N = 1. |
| F5 | Threads that each use `call_all` on a share of the sessions help only where threads run in parallel. | W = 0, N = 256: the statistic of `split` is below the statistic of `all` with the Rust host, and above it with the Python host, whose threads take turns. |
| R1 | In rounds, all agents agree on every round. | Every recorded `rounds` run, repeats included, finishes without an error: so every record check passed. In each of these runs, every agent received the same state after every round, and no member was excluded. |
| R2 | In rounds, the world's state does not depend on the order in which requests arrive. | For each N, the three `rounds` runs end in the same final state; and for each N of 4 or more, in each of these runs, at least half of the 220 rounds passed validation in an order other than the member order. |
| R3 | Applied in the order of arrival, the same requests leave different states. | For each N of 4 or more, the three `arrival` runs end in at least two different final states. |
| R4 | Rounds cost at most twice as much as applying requests on arrival, up to 64 agents, and at most three times with 256. | The statistic of `rounds` divided by the statistic of `arrival` is at most 2 for N = 1, 4, 16, and 64, and at most 3 for N = 256. |
| R5 | A Python owner in rounds serves 64 agents at 200 rounds per second. | `rounds`, N = 64: the statistic is below 5000 µs. |
| M1 | The client receives exactly the spikes of all ranks. | Every recorded run of part M, repeats included, finishes without an error: so every spike check passed. |
| M2 | The rank-0 pattern adds little to a call of up to 1788 spikes. | For R = 1, 2, 4, and 8 and S = 0 and 1788: the statistic minus the statistic of the same S without MPI is at most 30 µs (8 comparisons). |
| M3 | The rank-0 pattern adds at most a fifth to a call of 1 MiB. | S = 87381, for R = 1, 2, 4, and 8: the statistic is at most 1.2 times the statistic without MPI. |

A hypothesis holds when its decision rule holds. Three blocks give no confidence level.

Exploratory questions, without a hypothesis: `all` against `pool` and `split` with W = 1000 µs; the number of sessions from which `split` is faster than `all`; the cost per session at every N; how the round time grows with N; the 95th and 99th percentiles; the cost of each number of ranks; and where the time of a round of part R goes.

## 11. What the results do not show

- One computer and one operating system. On Linux, for example, a client waits for a full queue of connections instead of being refused, and threads are scheduled differently.
- The owners of part F only echo. W = 1000 µs is a sleep, which macOS extends to about 1.3 ms; owners that compute share the 16 cores, so a round over 256 computing owners takes longer.
- Part R measures the only implementation of the rounds profile, in Python. Most of its time per round is Python's: one thread at a time encodes a response, and every response carries the whole record. An owner in another language would differ. The agents are threads of one Rust process. The deadline of 60 s never applies; the SDK tests cover deadlines and exclusions.
- R2 shows that the order of arrival does not change this world's state, because its step is deterministic. A step that reads a clock or a random source is not made deterministic by the profile.
- Part M runs all ranks on one computer, where MPI uses shared memory. Across computers, both MPI and the client's connection cost more. NEST does not run in this benchmark; the spikes are generated.
- No other system is measured. The comparison benchmark compares single calls.

## 12. Pilot runs that informed this protocol

On 3 November 2026, before this protocol was fixed, pilot runs on the power adapter measured, among others (medians in µs; not results):

- Part F, Rust host, W = 0, at N = 1, 64, and 256: `all` 8.4, 231.5, 894.7; `pool` 19.0, 537.8, 2209.9; `split` 17.8, 183.4, 652.1; `sequential` 10.2, 823.4, 3795.4; `raw` 4.1, 101.9, 395.4. Python host: `all` 19.1, 718.0, 2853.7; `pool` 30.2, 1803.2, 8186.3; `split` 30.0, 1190.7, 4262.7; `sequential` 20.2, 1416.0, 6072.4; `raw` 5.0, 112.9, 425.0. With W = 1000 µs and N = 64: `all` 1510.7 (Rust) and 1789.2 (Python), against `sequential` 86,055 and 91,122.
- `split` was added after a review of a draft of this protocol found that `pool`, one thread for each session, is a weak alternative to `call_all` on a computer with many cores.
- Part R, at N = 1, 4, 16, 64, and 256: `rounds` 32, 146, about 600, about 2700, and about 16,400; `arrival` 23, about 88, about 410, about 1700, and about 7200. The `rounds` runs with the same N ended in the same state, and the `arrival` runs did not. With 256 agents, the owner took 5.0 ms to receive the requests of a round, 0.8 ms for the step and the record, and 9.5 ms until the last response was ready. Encoding a response with the record of 256 agents took 18.8 µs, against 2.9 µs without it.
- Part M, without MPI: 30 µs with 0 spikes, 52 µs with 1788, and about 1000 µs with 87381. With 1 to 8 ranks: 34 to 40, 60 to 68, and 1025 to 1087 µs. Every spike was exact.
- The pilots found that, when 256 agents connected to one owner at once, some connections were refused, because macOS keeps at most 128 connections waiting to be accepted. Since NCP commit `a74bf85`, `connect_unix` tries a refused connection again; the agents of part R also open their sessions one after another.
- After the pilots, each request of the rounds implementation waits on its own event instead of a shared condition. The time of a round did not change measurably.
- A run of the complete schedule with 20 rounds or 50 calls per run, before `split` was added, finished every configuration, with no failed and no disturbed run.
